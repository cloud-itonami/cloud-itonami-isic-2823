5. governor 拒否では「ない」保留 — phase gate と人間の却下

この 2 種類を HARD 拒否と一緒に数えると、actor の compliance 能力を実際より高く見せてしまう。どちらも governor は通しており、止めたのは別の層である。

opsubjectfact 型この fact が持つ violationgovernor は拒否したか
:flag-safety-concernconcern-2:approval-rejected[:approver-rejected]いいえ — governor はエスカレートさせ、人間が断った
分類が実際に判別していることの根拠。 人間の却下 fact は :violations [{:rule :approver-rejected}] を自分で持っている。もし (seq :violations) だけで HARD 拒否を数えていれば、この fact も governor の拒否として数えられてしまう。分類は fact の型（:t）を先に見るため、そうならない。同様に phase gate の保留は :phase-reason を持ち、violations は空である。

この観測は判別可能である。 承認者名と実行アクター名の集合に重なりが無いため、台帳の :actor（＝実行アクター）を承認者と読み違えた場合、その誤りはこのページ上で見える。本 renderer は :actor を承認者として一切扱っていない。
承認された opsubject台帳が記録した承認者 :bySSoT レコードに残った承認者らしいキー
実測した欠陥（このタスクでは修正していない）: 承認者の帰属が SSoT に残らない。
レジスタ全体（batches / equipment / maintenance / shipments / safety-concerns / records）を走査したが、承認者らしいキーは 1 件も存在しない。原因は実行経路の中にある: metalmachmfg.operation の :request-approval ノードは承認者を :payload に :approved-by として載せるが、metalmachmfg.store の commit-record! は :value のみを読み、:payload を一度も参照しない。したがって「誰が承認したか」は追記型台帳の :approval-granted fact にしか残らず、レジスタを見ただけでは分からない。台帳の :actor は実行アクターであって承認者ではないため、代用にもならない。
これは本タスク（renderer 追加）の範囲外として意図的に未修正のまま開示する。
